# Модульная структура CRM

## Что изменилось

Логика трёх ролей больше не редактируется внутри огромных HTML-страниц. Исходники находятся в `src/crm/`; сборщик создаёт совместимые страницы для действующего хостинга. При первом переносе все три страницы совпали с прежними побайтно. Отдельно внесены только защитные изменения загрузки необязательных компонентов и обновления экрана.

Это **модульность исходников с проверяемыми границами**, а не отдельные микросервисы и не изоляция памяти. Общие состояние, авторизация и хранилище ещё являются ядром приложения. Произвольная ошибка в ядре может затронуть несколько разделов; обещать абсолютную невозможность регрессий было бы неверно.

## Где работать

| Модуль | Ответственность | Проверка при разработке |
|---|---|---|
| `src/crm/orders/` | Карточка, список, статусы, назначение, действия мастера | `npm run test:module -- orders` |
| `src/crm/staff/` | Сотрудники, справочники, имена, графики | `npm run test:module -- staff` |
| `src/crm/payroll/` | Смены, дневной минимум, поздние закрытия, реестр выплат | `npm run test:module -- payroll` |
| `src/crm/finance/` | Финансовые поля, суммы и расчёт заказа | `npm run test:module -- finance` |
| `src/crm/analytics/` | Дашборд, показатели, фильтры аналитики | `npm run test:module -- analytics` |
| `src/crm/imports/` | Импорт, экспорт, распознавание и сопоставление | `npm run test:module -- imports` |
| `src/crm/quality/` | Контроль данных и AI-подсказки | `npm run test:module -- quality` |
| `src/crm/integrations/` | Подключение базы и публичные мосты | `npm run test:module -- integrations` |
| `src/crm/settings/` | Настройки приложения | `npm run test:module -- settings` |
| `src/crm/ui/` | Шаблоны экранов, стили, переключение и отображение | `npm run test:module -- ui` |
| `src/crm/core/` | Общие типы данных, утилиты и состояние | `npm run test:module -- core` и полный набор |
| `src/crm/bootstrap/` | Порядок запуска, привязка обработчиков, загрузка компонентов | Полный набор |
| `src/crm/roles/` | Оболочка и точка входа каждой роли | Полный набор |

`shared.js` содержит общие для ролей блоки; `owner.js`, `dispatcher.js`, `master.js` и комбинированные имена — реальные различия ролей. Список функций и их расположение находится в `src/crm/unit-catalog.json`. Для поиска достаточно `rg "function shiftPayroll" src/crm`.

## Отдельные интеграции и чистые расчёты

- `hosted-snapshot/profit-accounting.js`: чистый расчёт прибыли по переданным данным, без DOM и сети.
- `hosted-snapshot/avito-profit.js`: разбор расходов Авито.
- `hosted-snapshot/profit-bridge.js`: явный адаптер расчётов к авторизованной CRM; получает зависимости через `installMasterAIProfitBridge`.
- `hosted-snapshot/profit-ui.js`: экран прибыли.
- `hosted-snapshot/quality-monitor.js`: анализ данных и компонент мониторинга; не исправляет записи самовольно.
- `hosted-snapshot/telegram-ui.js` и `crm-api/telegram.php`: Telegram, привязки, доставка и ответы мастеров.
- `hosted-snapshot/crm-api/finance.php`, `quality.php`: отдельные серверные маршруты с действующими проверками доступа.
- `hosted-snapshot/visual-refinement.css`: общий визуальный слой. Перенос модулей не меняет оформление.

## Как внести изменение

1. Найти функцию или экран в соответствующем модуле. Не редактировать собранный `hosted-snapshot/index.html`.
2. Изменить существующий блок между `CRM_UNIT` / `CRM_END`, сохранив его стабильный ID. ID — идентификатор блока, его не нужно пересчитывать после каждой правки.
3. Выполнить `npm run build:crm`. Сборщик проверит синтаксис, принадлежность функций и зависимости, затем обновит все затронутые роли.
4. Выполнить `npm run test:module -- payroll` (или нужные модули, можно несколько через пробел).
5. Перед выпуском: `npm run gate:static`, `npm run test:architecture`, `npm run test:unit`, `npm run test:rules`, `npm run release:regru`. GitHub также выполняет серверные и релизные проверки.

Если добавляется новая функция: создать уникальный блок, зарегистрировать его в `manifest.json` с владельцем, символами и нужными ролями; добавить ID в правильное место рецепта каждой роли. Новые межмодульные обращения требуют проверки. Только после осмысленного просмотра изменений выполнить `node scripts/build-crm.mjs --update-contracts`, проверить diff контракта и собрать заново. Эта команда никогда не запускается автоматически в CI.

## Что защищает соседние разделы

- Новая неописанная межмодульная зависимость или неизвестная глобальная переменная блокирует сборку.
- Удалённые, повторные и незарегистрированные блоки, потерянные функции и синтаксические ошибки блокируют сборку.
- Роль не может незаметно получить блок, который ей не предназначен.
- Несобранные изменения и ручное изменение итогового HTML блокируют CI и упаковку релиза.
- Вызовы отображения разделов выполняются независимо. Проверка качества данных также имеет отдельную границу обработки ошибки.
- Ошибка загрузки финансового адаптера или мониторинга не прерывает запуск основной CRM; появляется видимое сообщение о недоступном компоненте.
- Тесты намеренно ломают модуль/зависимость, проверяют отказ сборки и продолжение работы остальных обработчиков. Проверяются также расчёты прибыли, зарплат и исключение повторных выплат.

## Ограничения и дальнейшая эволюция

Сборка сохраняет общий контекст исполнения существующего приложения. Это сделано, чтобы не переписывать одновременно авторизацию, хранение и финансовый учёт. Исходные фрагменты не следует подключать напрямую через `import`: исполняется собранная страница.

Следующий возможный этап — постепенно заменять внутренние связи явными сервисами с передаваемыми зависимостями, начиная с чистых расчётов. Для изменений общего состояния, схемы данных, авторизации и зарплат обязателен полный набор проверок. Локальный тест отдельного раздела не доказывает корректность всего продукта.

Структурный выпуск не мигрирует данные и не меняет постоянные адреса ролей. Для отката используются обычный предыдущий релиз и резервная копия опубликованных файлов.
