# Постоянная публикация CRM в REG.RU

## Как будет работать

Изменения в `hosted-snapshot/` → GitHub Actions запускает статическую проверку, unit-тесты и Firestore rules → собирает неизменяемый пакет и SHA-256 манифест → соединяется с REG.RU по явному FTPS → сначала скачивает действующие четыре страницы в приватный артефакт Actions → загружает пакет в скрытую staging-папку → сверяет байты обратным скачиванием → переносит файлы на место → проверяет публичные URL и контрольные суммы. При ошибке публикации проверенный прежний вариант восстанавливается автоматически. API CRM, конфиг подключения и данные заказов не входят в список публикации.

Обычный маршрут для будущего изменения: правка `hosted-snapshot/` → PR в `main` для проверок → merge в `main` запускает production deployment. Изменять рабочие страницы и данные заказов вручную в панели для обычных выпусков больше не требуется.

## Однократная настройка доступа

1. В ispmanager открыть **FTP-пользователи → Добавить FTP-пользователя**. Создать отдельного пользователя только для публикации CRM. Его домашняя директория должна быть ровно каталогом `candidate` сайта, а не домашним каталогом хостинга или `www`. Документация ispmanager указывает, что FTP-пользователь ограничивается выбранным домашним каталогом: [Add an FTP user](https://www.ispmanager.com/docs/ispmanager/add-an-ftp-user).
2. Включить FTPS/FTP over TLS для этого пользователя/сервера и зафиксировать точное имя сервера FTP из настроек REG.RU. Деплой использует стандартную проверку TLS-сертификата; проверка сертификата не отключается.
3. В GitHub `Settings → Environments` создать environment `production`. В `Settings → Secrets and variables → Actions → Variables` добавить:
   - `REG_RU_FTP_HOST` — hostname из ispmanager;
   - `REG_RU_FTP_PORT` — порт FTPS, обычно 21 для explicit FTPS, если панель показывает другое значение — использовать его;
   - `REG_RU_FTP_ROOT` — оставить пустым или поставить `.` если FTP домашний каталог уже указывает прямо в `candidate`.
4. В `production → Environment secrets` добавить:
   - `REG_RU_FTP_USER` — имя отдельного FTP-пользователя;
   - `REG_RU_FTP_PASSWORD` — его пароль.

Пароль не вставлять в чат и не хранить в репозитории. Эти секреты получает только job `deploy`, запускаемый для доверенной ветки `main` или вручную из `main`; проверки PR секреты не получают. Workflow имеет право только на чтение репозитория. Срок хранения приватного backup-артефакта — 90 дней.

## Что проверить перед первым включением

- FTP-пользователь видит в корне только файлы каталога `candidate` и может создать временный каталог.
- FTPS доступен снаружи и его сертификат действителен для указанного hostname.
- В environment `production` secrets и variables заданы без пробелов по краям.
- Workflow прошёл проверочные job после PR; после merge на `main` в Actions видны `verify` и `deploy`.
- Первый успешный релиз показывает четыре URL и совпадающие SHA-256; pre-image `crm-production-preimage-*` доступен в Actions Artifacts.

## Ограничения безопасности и откат

- Учётная запись ограничена только каталогом CRM и не использует пароль REG.RU/ispmanager.
- Во время выкладки файлы временно находятся в dot-папке внутри домашнего каталога FTP; после успеха папка очищается. Если job аварийно остановится, папка `.codex-staging/` может остаться — её можно удалить после проверки состояния страниц.
- При ошибке проверки публичной версии workflow восстанавливает предыдущие файлы из серверной временной копии. Параллельные production deployment сериализованы.
- Для ручного восстановления используйте приватный артефакт `crm-production-preimage-*` вместе с FTP-пользователем и контрольными суммами в его `manifest.json`.
- Никогда не включать в release allowlist `crm-api/`, `cloud-config.js`, `firestore-regru.js`, файлы БД, резервные выгрузки или заказы.
